## Decision

It is an additive, provider-owned File/SQLite capability that returns complete event envelopes for one tenant under one consistent observation, or a named refusal, without provisioning, repair or source writes. Keep the 0.2.1 physical formats and dependency family. Do not import the broader evolution branch.

The smallest useful result covers **history**, not a physical backup: retain every `RecordedEvent` field, including event identity, original schema version, stream version/global position, request identity, attribution and JSON data. Preserve the source files in place. Do not claim that decoded JSON retains original lexical SQL/frame bytes, that a newly calculated digest is an original receipt, or that event history includes command/claim/group tables, blobs, identities beyond the existing optional tenant identity, caches or materializations. Those omissions must be explicit. EKR's current acceptance requires the recorded event envelope; absent original operation/validation evidence still causes kernel migration refusal.

**No new tag is necessary to unblock EKR.** A public, immutable commit reachable from Eventlog main with verified source authority, required checks and its declared gate is a valid Git dependency anchor. Workspace governance distinguishes source publication from version release. The explicit commit-composition rule says no tag, release or version bump is required merely to compose a provider change. After verification, EKR advances **all three** `eventlog-core`, `eventlog-file`, `eventlog-sqlite` Git dependencies to the same full `rev`, together with `Cargo.lock`. Do not claim a new release or retain the old tag selector beside that revision. The prior provider report's demand for a normal exact-tag release is stricter than necessary and is corrected here.

## Minimal contract choices to record before dispatch

Recommended names are proposals, not existing API:

- A small `InspectHistory` capability returning an owned `HistoryInspection`, implemented only by separate `FileHistoryInspector` and `SqliteHistoryInspector` types. No `EventStore` implementation, raw connection, writable store, callback or default paginated fallback escapes.
- `HistoryInspection` contains the requested typed tenant, **optional original stored tenant identity**, and every `RecordedEvent` in ascending global position. Global gaps are valid; per-stream history must have the provider's valid ordering. Existing identity is never minted or normalized. `None` plus empty history means no recorded evidence of the tenant, not proof of a provisioned empty tenant. This differs deliberately from capture's mandatory-identity criterion: EKR's current adapter does not call `stream_identity`, so requiring it would reject ordinary EKR legacy stores.
- Explicit finite limits bound source admission/read size, number of returned events and retained envelope bytes. Zero is a real cap, arithmetic is checked, and limit failure returns no partial successful result. File input length must be checked before whole-log allocation; SQL per-row lengths and aggregate limits must be checked before owned accumulation. These caps are not a promise of an exact process-memory bound.
- Named missing-source, unsupported-source, recovery-required, corrupt-source, redacted-history, busy/source-changed and limit refusals. A caller can report missing history but cannot manufacture a successful conversion from a partial value. Freeze exact variants and error precedence in the short design before tests.
- No physical fingerprint promise is needed for this first API. Provider consistency and unchanged source bytes are required. If a boundary witness is added, label whether it is an original File manifest coordinate or a newly computed logical digest; neither a SQL maximum position nor a reserialized-record digest proves the original database file bytes. Command/group/claim export is a separate future capability if a consumer actually requires it.

These transient coordinates/limits should get a minimal typed home under `ess/inspection/`, following the existing `ess/capture/` value-only precedent. Reuse `RecordedEvent`, `TenantId` and Rust payload types; introduce no persistent entity, lifecycle or generic JSON input. The coordinator must validate the proposed specification before recording it as an established typed contract. No draft specification was validated during this scope task.

## Exact implementation route

**Core:** `crates/eventlog-core/src/lib.rs:502` already defines the complete `RecordedEvent`; add an inspection module and exports without changing existing traits or persisted encoders. Separate inspection errors avoid breaking exhaustive matches on the existing public error enum. `BoxFuture` already supplies the async boundary.

**File:** ordinary `Journal::open` at `crates/eventlog-file/src/journal.rs:113` must not be called. Add a strict sibling using existing manifest/frame decoding. Require physical existing root, lock, manifest and log; reject pending append/privacy entries including dangling links using `symlink_metadata`; hold the existing interprocess writer lock through validated observation; do not initialize, repair, truncate, clean staging or collect blobs. Use the current private `state.rs::State::replay` and its typed `Op::Event`/identity state, not an EKR parser. Validate manifest committed length/digest and refuse unproven suffixes. A finite busy refusal is preferable to an unbounded lock wait. The donor uses a read/write descriptor to the existing lock without writing its bytes: decide/document whether a read-only descriptor can support the target locking primitive; do not confuse handle permissions with proof of no source changes.

**SQLite:** `crates/eventlog-sqlite/src/lib.rs:106–137` routes ordinary construction through WAL setup and DDL; bypass it entirely. Use a new READ_ONLY/no-CREATE connection with URI parameters controlled by the provider, retain ordinary locking/change detection, and use one deferred read transaction across schema admission, optional identity and history. Do not use `BEGIN IMMEDIATE`, `immutable=1` on live paths, writable `open_existing`, or automatic recovery. Reuse `read_event` (`lib.rs:2196`) and schema knowledge; perform exact admission for the published supported event/identity shapes and reject incompatible namespace objects/triggers/views before assuming provider ownership. Do not require evolved blob columns when blobs are not inspected.

The coordinator accepts **strict cold-database support first**, with named refusal of unsupported WAL/hot-journal conditions. Adopt that bounded target instead of building a full live-capture subsystem. A healthy SQLite fixture must demonstrate actual successful reading without source changes; refusal tests alone do not establish a usable SQLite inspector. Ordinary 0.2.1 opening sets persistent WAL mode, so explicitly measure whether a cleanly closed, checkpointed 0.2.1 database qualifies: sidecars being absent does not itself prove rollback mode or permission to initialize SHM. If it does not qualify, report that concrete support limit. Do not checkpoint or switch the source's journal mode merely to make acceptance pass, and do not treat an unverified quiescence assertion as authority for immutable mode.

Pinned rusqlite 0.37/libsqlite3-sys 0.35 bundles SQLite 3.50.2. Its Unix `readonly_shm=1` implementation is a candidate primitive for forbidding writable/created SHM while preserving normal SQLite consistency, **not measured acceptance**. For unsupported platforms/configurations, return a named capability refusal. For healthy committed WAL, either include its events under the strict read boundary or refuse explicitly; never report only main-file history. Required SHM initialization, hot-journal recovery or source repair must refuse without side effects, including handle close. A writer changing its own files during a concurrency test is not an inspector write: prove inspector nonmutation with no competing writer, and prove snapshot-or-refusal separately under writer/checkpoint/privacy interleavings.

## Incidental payload-storage note

Eventlog already has the concrete mechanism needed to move EKR object bytes out of event data: `EventStore::{put_blob,get_blob,delete_blob}` (`eventlog-core/src/lib.rs:972–1005`), File blob objects (`eventlog-file/src/lib.rs:787–846`) and SQLite tenant/digest blob storage (`eventlog-sqlite/src/lib.rs:1391–1432`). The core documentation explicitly says events name digests while erasable content lives in blobs. JSON numeric arrays in EKR `ObjectRecord.bytes` are still payload bytes; encoding does not satisfy invariant 8.

The published SQLite implementation currently accepts conflicting duplicate digest puts through `ON CONFLICT DO NOTHING` and returns blob bytes without recomputing content integrity. Evolution's implemented `blob-binding-conflicts` and `sql-blob-read-integrity` directly address those gaps; active capture also exposes retained content. Thus there is a provider-owned route, without an EKR-private storage fork, but no claim here that those improvements are already published. Schedule the EKR storage-policy/migration decision with appropriate verified upstream support for P2/P6, preserving legacy source and provenance. Do not expand this history-inspection unit to move existing object records, add blob migration, delete payloads or alter privacy policy.
